# 版本 1：从确定性工作流开始

> 用最小架构交付一个可预测的企业研究报告产品。

## 它解决什么问题

第一版不需要自主 Agent。用户真正要的是一份结构完整、来源可追踪、按时返回的报告；固定流程已经能验证需求、数据源和质量标准，也提供以后比较的基线。

## 核心定义与工作原理

流程固定为 intake→scope→retrieve→draft→validate→deliver。代码拥有全部控制权，模型只完成限定的理解、摘要和写作任务。任务状态记录输入、研究范围、证据、草稿、验证结果和最终产物；每一步都有结构化契约。

### 架构视图（Architecture View）

分析时固定追问：谁拥有控制权，状态存在哪里，模型能决定什么，失败从哪里恢复，人工在哪个边界介入，运行证据如何被观察。

### 产品视图（Product View）

用户看到明确范围确认、阶段进度和可下载报告。首版重点验证完成率、首次可用率、来源覆盖率、端到端时延和单份报告成本，而不是炫技式自主行为。

## 简单实践

设计一张六阶段流程图，并为每阶段写输入、输出、超时与失败提示。用三个不同复杂度的研究请求做纸面推演，记录预计调用数、人工步骤和用户等待点，不运行代码。

实践只要求架构图、状态或消息契约、失败路径和产品指标，不要求安装依赖或运行代码。

## 正常场景

任务按约定入口进入，编排层保留业务状态，各节点或 Agent 产出结构化结果，质量门控制下一阶段，用户获得可理解的进度与最终产物。

## 失败与恢复场景

模型超时、工具失败或子任务质量不足时，区分可重试、可降级和必须人工接管的错误。恢复应依赖业务状态或检查点，而不是把整段任务盲目重跑。

## 什么时候使用

- 核心抽象与任务形态一致。
- 团队能运维它的状态、观测和升级路径。
- 能满足审批、权限、恢复与成本约束。

## 什么时候不要使用

需求高度开放、步骤无法预先枚举时，固定工作流可能频繁走人工例外。但在没有证据前，不要用 Agent 自主性替代产品规则。

## Trade-offs

| 获得 | 代价 |
| --- | --- |
| 更清晰地表达目标架构 | 增加建模和治理成本 |
| 复用运行与生态能力 | 接受版本、依赖和迁移成本 |
| 提升自主性或协作能力 | 增加时延、成本与故障面 |

## 产品视角

- **用户与业务问题**：解决哪个可量化瓶颈？
- **产品价值**：提升成功率、速度、可控性还是覆盖范围？
- **用户体验**：进度、等待、切换和失败是否可理解？
- **自主性边界**：哪些判断交给模型，哪些由代码或人决定？
- **数据与权限**：状态、敏感数据和工具权限如何隔离？
- **失败与降级**：能否重试、续跑、切回简单流程或人工处理？
- **产品指标**：完成率、P95 时延、单任务成本、人工介入率、恢复成功率。

## 框架中的对应实现

普通应用代码、任务队列与结构化模型调用即可；任何框架中的 Sequential Workflow 都能表达这一版。
